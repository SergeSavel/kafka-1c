# AGENTS.md

Инструкции для ИИ-агентов, работающих с кодом этого репозитория.

## О проекте

Подсистема «Кафка» для «1С:Предприятие 8.3» — интеграция с Apache Kafka через внешний HTTP-шлюз
([kafka-gateway](https://github.com/SergeSavel/kafka-gateway), порт по умолчанию 8086). 1С не работает с брокерами
напрямую: все операции producer/consumer/admin выполняет шлюз, подсистема ходит в него по REST.

Исходники — проект 1C:EDT в `configuration/` (формат `.mdo` + `.bsl`). Язык кода — русский
(`scriptVariant = Russian`), все имена метаданных и методов кириллицей с префиксом «Кафка».

## Сборка, запуск, тесты

CLI-сборки, линтера и автотестов в репозитории нет — весь цикл идёт через 1C:EDT:

1. File → Import → «Существующие проекты» / 1C:Enterprise project, каталог `configuration/`.
2. Запуск/отладка из EDT (управляемое приложение) либо выгрузка в конфигуратор/CF.
3. Для реального обмена нужен поднятый kafka-gateway и доступные брокеры.

Изменения в коде правятся в `.bsl`; при добавлении/переименовании объектов метаданных обязательно синхронно
правится соответствующий `.mdo` и `Configuration.mdo` (список объектов конфигурации) — иначе EDT проект не соберётся.

Проверить результат обмена без EDT нельзя; при изменении логики обмена описывай, что именно нужно проверить руками.

## Архитектура

Слои (сверху вниз):

```
Клиентские формы / регламентные задания
  └─ КафкаВызовСервера        тонкая обёртка «&НаСервере» (Выгрузить/Загрузить/ОбновитьРегламентныеЗадания)
      └─ КафкаСервер           ядро: сценарии обмена, сериализация, параллелизм, позиции
          └─ Обработка КафкаАдаптер   низкоуровневый HTTP-клиент шлюза (методы Producer*/Consumer*/Admin*)
              └─ HTTP-шлюз → Kafka
```

Ключевые файлы:

- [КафкаСервер/Module.bsl](configuration/src/CommonModules/КафкаСервер/Module.bsl) — области
  `АвтоВыгрузка`, `АвтоЗагрузка`, `РучноеИспользование`, `СлужебныеФункции`, `СериализацияJSON/XML/AvroAsXml`.
- [КафкаАдаптер/ObjectModule.bsl](configuration/src/DataProcessors/КафкаАдаптер/ObjectModule.bsl) — `Инициализировать`
  создаёт `HttpСоединение`, дальше по методу на каждый эндпойнт шлюза.
- [КафкаПовтИсп/Module.bsl](configuration/src/CommonModules/КафкаПовтИсп/Module.bsl) — кэш метаданных
  (`ИндексМетаданных`, `ОписаниеОбъектаМетаданных`) и повторно используемые настройки.
- [docs/serdes.md](docs/serdes.md) — контракт сериализации ключей и значений: что приём получает по каждому сердесу
  и что обработчик обязан вернуть при выгрузке. Меняя `ДесериализоватьЗначение` или сериализаторы, синхронизируй документ.

### Выгрузка (1С → Kafka)

Управляется **планом обмена**: реквизит `Узел` справочника `КафкаШины` имеет тип `ExchangePlanRef`, но самих планов
обмена в базовой конфигурации нет — их даёт конфигурация-хост или расширение. `КафкаСервер.ПолучитьИзменения(Узел)`
строит запрос по составу плана обмена и забирает зарегистрированные изменения; порядок таблиц задаёт
`Обработка.ВыгружаемыеОбъектыМетаданных()` (колонка `Порядок` — между порядками пул потоков полностью дожидается
завершения). На шину создаётся один Producer в шлюзе, пакеты объектов раздаются в фоновые задания
(`ВыгрузитьПакетОтдельныйСеанс`), пул потоков — `ИнициализироватьПараллелизм` / `ДождатьсяОсвобожденияПулаПотоков`.

### Загрузка (Kafka → 1С)

`Загрузить` получает список читаемых разделов темы, случайно раскидывает их по `ОбменКоличествоПотоков` потоков и
запускает `ФоновыеЗадания.Выполнить("КафкаСервер.ЗагрузитьРазделы", …)` — поэтому `ЗагрузитьРазделы` должна оставаться
экспортной с сериализуемыми параметрами. Сеанс чтения ограничен по времени (`ОбменДлительностьСеанса`,
`ПриемВРеальномВремени`).

Позиции чтения хранятся в собственном регистре `КафкаПозиции`, а не в Kafka: `enable.auto.commit=false`,
`auto.offset.reset=earliest` (см. `КонфигурацияПолучателя`). `ЗафиксироватьПозицииЧтения` намеренно падает, если
активна транзакция — фиксация позиции не должна попадать внутрь транзакции обработки данных.

### Конфигурации клиентов

`КонфигурацияБазовая` → `КонфигурацияОтправителя` / `КонфигурацияПолучателя` → `КонфигурацияШины`: базовые параметры,
`client.id` (из `КафкаПереопределяемый.ИдентификаторИнфобазы`) и SASL берутся из справочника `КафкаКластеры`, поверх
накладываются табличные части кластера и шины. Добавляя параметр
Kafka, правь соответствующую функцию, а не место вызова.

### Точки расширения

Базовое ядро не предназначено для правки — функциональность наращивается надстройками и расширениями (см. [NOTICE](NOTICE)):

- [КафкаПереопределяемый](configuration/src/CommonModules/КафкаПереопределяемый/Module.bsl): `ЭтоБэкап`,
  `РазрешенОбменБэкапов`, `ПолучитьОбработку(Шина)`, `ГруппаПолучателей`, `ПользовательПоУмолчанию`,
  `ИдентификаторИнфобазы`, `ИмяИнфобазы`.
- Внешняя обработка из реквизита `Обработка` шины реализует протокол обмена: выгрузка — `ВыгружаемыеОбъектыМетаданных`,
  `Перед/После…Шины|Таблицы|Пакета|Объекта`, `СообщениеКлюч`, `СообщениеЗначение`, `СообщениеСуффиксТемы`;
  загрузка — `ПередЗагрузкойРаздела`, `ПослеЗагрузкиРаздела` плюс процедура из реквизита `ПриемПроцедура`.
  Реквизиты `Шина` и `Узел` подставляются в обработку через `УстановитьРеквизитыОбработки` (только если объявлены).

### Регламентные задания

`КафкаВыгрузка` / `КафкаЗагрузка` — шаблоны; экземпляры на каждую шину создаются, обновляются и удаляются
автоматически из `ПриЗаписи`/`ПередУдалением` справочника `КафкаШины` через
`КафкаВызовСервера.ОбновитьРегламентныеЗадания`. Расписание и пользователь берутся из реквизитов шины — не заводи
задания вручную.

## Соглашения

- Каждый `.bsl` начинается с русского заголовка Apache 2.0 — копируй его в новые модули, в существующих не трогай.
- Код разбит на `#Область … #КонецОбласти`; в `КафкаАдаптер` по публичному методу на эндпойнт шлюза, сам запрос
  выполняют общие `ВыполнитьPost` / `ВыполнитьGet`, публичный метод разбирает тело/код ответа.
- Ошибки шлюза — через `Адаптер.КодОтвета` / `Адаптер.ОписаниеОшибки`; ошибки обмена — в `ЗаписьЖурналаРегистрации`
  с событием `"Обмен данными.Кафка.<наименование шины>"`; сообщения пользователю — `КафкаСервер.СообщитьПользователю`.
- Ресурсы шлюза (Producer/Consumer/Admin) освобождаются в `Попытка…Исключение` — при добавлении новых веток выхода
  сохраняй парный `…Release`.
- Модальность и синхронные вызовы запрещены (`modalityUseMode = DontUse`), режим совместимости 8.3.10 —
  не используй возможности более новых платформ.
- Версия релиза фиксируется в двух местах одновременно: `<version>` в [Configuration.mdo](configuration/src/Configuration/Configuration.mdo) и `КафкаСервер.ВерсияПодсистемы()`.
- Имена тем валидируются в `КафкаШины.ObjectModule.ПередЗаписью`: строчные латинские буквы, цифры, `-`, `_`, `.`,
  и `*` только последним символом (шаблон).
- Коммиты и документация — на русском.
- [README.md](README.md) — визитная карточка для пользователей: сначала функциональные возможности, технические
  подробности реализации туда не тащим. Номера версий в документации не указываются вообще — они живут только в
  исходниках.
- [CHANGELOG.md](CHANGELOG.md) — тоже для пользователей и внедренцев, продуктовым языком: что изменилось в поведении и возможностях, какие симптомы были у дефектов, что делать при обновлении. Имена модулей, функций, методов шлюза, счётчики строк и прочие детали внутренней реализации туда не выносим — они нужны в коммитах, а не в истории изменений. Границы релизов определяются по тегам.
